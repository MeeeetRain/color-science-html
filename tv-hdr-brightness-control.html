HDR Brightness Control

电视亮度，不再只是背光强弱

把 HDR 亮度控制重新定义为 Reference White、Display Headroom、Tone Mapping 与 Panel Drive 的联合决策。核心原则只有一句：锚住普通白，让面板峰值的波动只体现在高光 roll-off 上，绝不污染中间调和 UI。

核心逻辑

用户调亮度时，系统真正调整的是普通白有多亮、高光保留多少空间、中间调如何适配观看环境，而不是简单把整块面板推亮。Headroom 不是可调输入，它是 Peak_eff 与 Reference White 的比值——一个被动导出的余量。极暗部要被保护，不能跟着亮度滑杆被直接拉高或压低。

电视 HDR 亮度控制不再直接等同于背光强弱，而是由 Reference White、Display Headroom、Tone Mapping 和 Panel Drive 共同决定。
① Reference White 是锚点

SDR 白、HDR diffuse white、UI、字幕都对齐到它。它是用户"亮度"真正改变的量。

② Peak 是窗口的函数

OLED/Mini-LED 受 ABL 限制，峰值随高光窗口面积逐场景漂移。Peak_eff 不是常数。

③ 波动吸收进高光

Peak_eff 起伏时，diffuse white 锚死不动，所有变化都被 knee 之后的 roll-off 吸收。

两套核心模式

一个模式负责准确，一个模式负责环境适配。产品层越清楚，底层曲线越不容易互相打架。

Filmmaker / 准确模式

尊重内容原始 HDR 意图：亮度调的是 Reference White 锚点，中灰到参考白逐渐跟随白点变化；极暗部保留原始 PQ 暗部结构，优先保留 headroom，knee 之前严格跟随 PQ EOTF 的相对关系。

  • RW用户亮度在 100-300 nits 区间调白点（暗室影院到明亮客厅），仅受 Peak_eff / 4 物理上限约束。
  • Headroom建议不低于 4x，用来保留高光层次。
  • Tone Mappingknee 前保持 PQ 斜率（RW=203 时与 1:1 完全重合），超出面板能力时才进入 soft roll-off。
  • 用户控制亮度影响 Reference White 与中灰以上观感，暗部用 toe 保护平滑过渡，绝不去抬黑位变成明亮模式。

明亮模式 / Bright Room HDR

提高高环境光下的可见性：提高普通白，并按环境光在中段抬升暗部（黑端锚定、细节按比例保留），允许压缩部分高光层次。

  • RW约 200-450 nits，由用户亮度和环境光共同决定 RW_target。
  • Headroom保底 2.2x-3x，不能让普通白吃光 HDR 空间。
  • Tone MappingRW 以下做可见性增益，RW 以上更早进入 shoulder。
  • 用户控制亮度滑杆影响 RW target，而不是直接拉满背光。

真实可用的曲线模型

横轴是输入 PQ 绝对亮度（对数），纵轴是显示输出亮度（对数）。亮度滑杆改变 Reference White 锚点；极暗部保持黑位和暗部层次，中灰到参考白逐渐过渡到新的白点增益。而拖动「高光窗口」让 ABL 改变 Peak_eff 时，RW 锚点不随面板波动漂移，只有 knee 之后的 roll-off 在吸收变化。黄色带是当前可用的高光 headroom。

计算链路 · 跟随滑杆实时复算

上面的曲线不是画出来的，是用下面这条链路算出来的。每一步都把当前控件的数值代入，拖动滑杆时算式同步更新——可以逐步对照验证。

① 有效峰值 Peak_eff（ABL 折算）

面板峰值能力是在 10% 窗口下标定的。高光窗口越大，功率越分散、可持续峰值越低，由 ABL 折算系数体现。它不会直接改变 Reference White 的目标，而是先降低 Peak_eff，再通过 RW 上限和高光 shoulder 改变曲线形状。

② Reference White 目标 RW_target

这是用户「亮度」真正改变的量。准确模式只缩放白点；明亮模式在基础白点上叠加环境光与用户增益。

③ RW 物理上限 RW_max

为了给高光留出至少 H_min 倍的余量，普通白不能超过 Peak_eff / H_min。这一步保证 headroom 有下限。

④ 最终 RW_final

取目标与上限的较小者。一旦上限生效（大窗口或低 peak），白点被钳住——这正是真实功率约束。

⑤ 高光 Headroom（结构性保底）

因为 RW_final ≤ Peak_eff / H_min，所以 headroom = Peak_eff / RW_final 必然 ≥ H_min。白点永远吃不光 HDR 空间。

⑥ Knee 拐点

从 RW 往上数 availableStops × kneeFraction 档进入 shoulder。knee 之前按 midSlope 线性跟随，之后开始 roll-off。

⑦ Shoulder 收敛 + 暗部保护

knee 之上用指数 shoulder 渐近（不硬切）Peak_eff；RW 之下不做整段纯增益，而是先保护极暗部，再用 smoothstep toe 把 1 nit 以上的暗部/中间调平滑过渡到 RW 增益。环境光提亮只作用在中段，黑端与 RW 端斜率均为 0。

为什么是 203 nits：ITU-R BT.2408 把 HDR Reference White（diffuse / graphics white）定在 203 nits。PQ（SMPTE ST 2084）是绝对亮度编码，所以"调亮"不能简单整体加增益，而要重新选定这个锚点再决定锚点之上如何 roll-off。

算法框架

页面里的曲线不是装饰图，而是用这组约束动态生成：203 nits 内容白映射到 RW_final，Peak_eff 由面板能力经 ABL 折算，knee 由剩余 headroom 决定，高光用指数 shoulder 接近 Peak_eff，极暗部用 toe 保护避免亮度滑杆直接裁切或抬黑。

有效峰值Peak_eff = ABL(Peak_cap, window)
RW 上限RW_max = Peak_eff / Headroom_min
最终 RWRW_final = min(RW_target, RW_max)
暗部 toegain = mix(1, RW/203, smoothstep)

电视内的色彩处理流程（HDR 输入）

上面的亮度控制逻辑不是孤立的一条曲线，它嵌在电视 SoC 的完整色彩管线里。下面按信号流动顺序走一遍：哪一步该做什么、绝对不能做什么，以及本页的 RW / Peak_eff / tone curve 分别接在哪里。

① 解码与色度上采样 YCbCr 4:2:0 · 限范围

HDMI / 流媒体解码后通常是 10-bit YCbCr 4:2:0、BT.2020-nc、PQ 编码、限范围（64–940）。先做色度 4:2:0 → 4:4:4 上采样，再展开到全范围。

要点：这一步不做任何"亮度"操作。YCbCr 的 Y' 不是真实亮度（non-constant luminance），在这里调亮会顺带改变色度、引起色相偏移。

② 矩阵变换 + EOTF 线性化 进入线性光 RGB

YCbCr → R'G'B'（BT.2020 矩阵），再过 ST 2084 PQ EOTF（1D LUT）得到线性光 RGB——数值直接对应绝对亮度 nits（0.0001 ~ 10000）。HLG 输入则按 BT.2100 OOTF 折算到同一线性域。

要点：之后所有亮度与色彩决策都必须在线性光域做；管线内部精度至少 16-bit 浮点（或等效定点），否则 0.1–1 nit 的暗部细节会量化成 banding——这正是前面暗部模型强调"深黑锚定"的硬件前提。

③ 元数据解析 + 帧统计 控制面

解析静态元数据（MaxCLL / MaxFALL、Mastering Display）与动态元数据（HDR10+、Dolby Vision、ST 2094-50 的 Reference White Anchor）；同时对当前帧做直方图统计：APL、高光像素占比、场景切换检测。统计结果送入 ABL 功率模型，得到本帧的 Peak_eff。

要点：demo 里手动拖的「高光窗口」滑杆，在真机上就来自这一步的实时统计。这里也是 RW_target（用户亮度 + 环境光传感器）汇入的地方。

④ Tone Mapping 线性光 RGB · 本页核心

在线性光域执行暗部保护 + RW 锚定 + knee + shoulder——就是「计算链路」生成的那条曲线。工程关键：不要逐通道（per-channel R/G/B）套曲线，高光会偏色（白炽灯变黄、天空转青）。正确做法是取亮度代理 m = max(R,G,B)（或 ICtCp 的 I 通道），算增益 g = T(m) / m，再三通道同乘 g，保住色相与饱和度比例。

要点：曲线每帧由控制面更新成 1D LUT，数据面逐像素只做查表 + 乘法——RW / headroom 决策的全部计算量都在控制面，像素侧零额外成本。

⑤ 色域映射 线性光 RGB

BT.2020 只是容器，内容实际多为 P3 体积；面板原生约 90–98% P3。用 3×3 矩阵 + 边界软压缩（或 3D LUT）把超出面板色域的颜色压回来，避免硬裁剪让饱和色丢掉层次。

要点：顺序在 tone mapping 之后——亮度改变后可显示的色域体积也变了（越亮可用饱和度越小），先 tone map 才知道每个像素真正落在哪个亮度层。

⑥ 图形 / UI 合成 视频平面 + 图形平面

视频平面（已 tone map）与图形平面（UI、字幕，通常 SDR/sRGB）分开处理：图形先线性化，把 SDR 白对齐到 RW_final 并 clamp ≤ RW，再与视频在线性域做 alpha 混合。

要点：这就是读数区「UI & 字幕 clamp」的落点。若在非线性域混合，半透明边缘会出现深色/亮色镶边；若不 clamp，白色 UI 会被推进高光区抢功率、刺眼。

⑦ 校准与面板驱动 面板域

过校准 3D LUT（白点、灰阶、色域微调），再转面板驱动信号。OLED：直接电流驱动 + ABL/TPC 钳制；Mini-LED：把目标图像分解为背光矩阵 × LCD 透过率两层，给高光区域保留功率预算。最后以 ≥10-bit + 时空抖动输出到面板位深。

要点：第③步的 Peak_eff 估计和这里的功率分配是同一个闭环——本帧的分配结果决定下一帧统计到的 Peak_eff。

控制面 / 数据面分离 + 时间平滑：RW_final、Peak_eff、tone curve、色域压缩参数都属于控制面，按帧或场景更新；逐像素工作全部走 LUT。控制量更新必须做时间平滑（如 IIR 滤波）：场景内缓变、场景切换处允许快变——否则曲线跳变会被观众看成闪烁或"呼吸"。这也是把 ABL 波动吸收进高光 roll-off 之外，第二道防呼吸感的闸门。
