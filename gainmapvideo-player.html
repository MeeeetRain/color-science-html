给视频版 gain map 做一个
能真正点亮 EDR 的播放器 Building a player for video gain maps
that actually lights up EDR

这是一篇第一人称的复盘：我们做了一个向后兼容的「视频版 gain map」格式 GainmapVideo，然后为它做播放器。过程里走了两条路——自研原生 Metal 实时播放器，和 IINA 插件转码方案——并在最后撞上一个反直觉的教训：让 HDR「不亮」的，其实根本不是代码。 A first-person retrospective. We built GainmapVideo — a backward-compatible "video gain map" format — and then built players for it. Two roads: a native real-time Metal player, and an IINA transcode plugin. Along the way we hit a counter-intuitive lesson: what kept HDR from "lighting up" was not the code at all.

为什么要做「视频版」gain mapWhy a video gain map

gain map 的思路是：底层存一张普通 SDR 画面,额外再带一张「增益图」,告诉显示器在有 HDR 余量时每个像素该提亮多少。SDR 播放器无视增益图照常显示,HDR 播放器则按显示器当前能力重建出 HDR。这套做法在静态图上已经标准化(ISO 21496-1:2025,Apple Adaptive HDR / Google Ultra HDR / Adobe 都收敛到它),但视频至今没有等价标准。GainmapVideo 填的就是这个空。 A gain map stores an ordinary SDR picture plus a "gain" image that tells the display how much to brighten each pixel when HDR headroom is available. SDR players ignore the gain map; HDR players reconstruct HDR scaled to the display's current capability. This is standardized for still images (ISO 21496-1:2025 — Apple Adaptive HDR, Google Ultra HDR, Adobe all converge on it), but there is still no equivalent for video. GainmapVideo fills that gap.

底层就是标准 SDR 视频。QuickTime / VLC / 浏览器 <video> 当普通片子放,完全无感。The base is a standard SDR video. QuickTime / VLC / browser <video> play it as an ordinary clip, none the wiser.

重建数学The reconstruction math

每个像素:先把 SDR 解到线性,再用增益码值算出对数增益,按一个随显示器余量变化的 weight 施加提亮。weight 把「显示器现在有多少 HDR 余量」映射到 0~1,这就是自适应的核心。 Per pixel: linearize the SDR, derive a log gain from the gain code value, and apply it scaled by a weight that depends on the display's headroom. The weight maps "how much HDR headroom the display has right now" to 0..1 — that is the adaptation.

g_log = GainMapMin + pow(gCode, Gamma) · (GainMapMax − GainMapMin)
weight = clamp( (log2(displayHeadroom) − HDRCapacityMin) / (HDRCapacityMax − HDRCapacityMin), 0, 1 )
hdr   = (srgbEotf(sdr) + OffsetSDR) · 2(g_log · weight) − OffsetHDR

原生播放器把 displayHeadroom 取成每一帧实时的 EDR 余量,所以你调一下屏幕亮度,高光的强度立刻跟着变。这跟我们在浏览器里验证过的 WebGL 重建是逐字一致的公式。 The native player reads displayHeadroom as the live, per-frame EDR headroom, so nudging screen brightness changes highlight intensity instantly. It is the exact same formula we validated earlier in the WebGL reconstruction.

为什么 IINA 走转码而不是实时?因为 mpv 的自定义 shader 只能作用在单路视频上,没法把第二路实时解码的 gain 轨当成逐帧更新的纹理喂进去;能塞两路的 --lavfi-complex 又做不了我们这种逐像素浮点合成。于是用「mpv 的强项(EDR 输出)绕开它的弱项(双路输入)」——代价是转码。 Why does IINA transcode instead of rendering live? mpv's custom shaders operate on a single video; there is no clean way to feed a second, live-decoded gain track as a per-frame texture, and the --lavfi-complex path that does take two inputs can't do our per-pixel float compositing. So we lean on mpv's strength (EDR output) and route around its weakness (dual input) — at the cost of a transcode.

EDR 显示链路The EDR display path

原生播放器的输出端是关键。我们用一个 CAMetalLayer,打开 wantsExtendedDynamicRangeContent,色彩空间设为 extendedLinearSRGB,像素格式 rgba16Float。在这个 layer 上:1.0 = SDR 白,>1.0 就用显示器的 EDR 余量。我们的片源是 BT.709/sRGB,shader 直接输出线性 sRGB,与 layer 的色域逐位对齐、零转换。mpv 走的也是同一类 Metal → macOS EDR 管线,所以两个播放器在「输出端」都靠谱。 The native player's output side is the crux. We use a CAMetalLayer with wantsExtendedDynamicRangeContent on, colorspace extendedLinearSRGB, pixel format rgba16Float. On this layer 1.0 = SDR white and >1.0 uses the display's EDR headroom. Our source is BT.709/sRGB and the shader outputs linear sRGB, so it matches the layer's gamut exactly, no conversion. mpv uses the same class of Metal → macOS EDR pipeline, so both players are solid on the output side.

那个反直觉的教训The counter-intuitive lesson

⚠️ 让 HDR「不亮」的不是 bug,是屏幕亮度⚠️ What kept HDR dark wasn't a bug — it was screen brightness

我们排查了很久「为什么不进 HDR」:浏览器、IINA、原生播放器轮流试,改 probe、改 colorspace、改 shader……结果真正的根因是:macOS 在高亮度下根本不给 SDR 白以上的余量。系统报告的 maximumExtendedDynamicRangeColorComponentValue 在高亮度时坍缩到 1.0——任何 app 都没有空间把 HDR「亮出来」。渲染一直是对的,只是无处可亮。 We spent a long time on "why won't it enter HDR" — cycling through browser, IINA, native player, tweaking the probe, the colorspace, the shader… The actual root cause: at high brightness macOS reserves no headroom above SDR white. The system's maximumExtendedDynamicRangeColorComponentValue collapses to 1.0 — no app has room to show HDR. The rendering was correct all along; there was simply nowhere to be bright.

✅ 调低亮度,余量就回来了✅ Lower brightness, and the headroom returns

把屏幕亮度调低,current 余量立刻从 1.0× 往上爬(我们见过 6×,潜在 16×),weight 随之从 0 涨到 1,画面里的高光肉眼可见地亮过 SDR 白。排查 EDR 不亮,先调低亮度看余量,别急着怀疑代码。 Lower the brightness and the current headroom climbs from 1.0× (we saw 6×, potential 16×); the weight rises 0 → 1 and highlights visibly exceed SDR white. When EDR won't light up, lower brightness and check the headroom before suspecting the code.

硬件编码,以及一个意外发现Hardware encoding, and a surprise

IINA 路线最初用软件 x265 编 HDR10,首开慢。我们给 gvtools 加了 Apple Silicon 硬件 HEVC(hevc_videotoolbox)选项。但实测发现:转码慢的瓶颈不是编码器,而是 Python/numpy 做 gain 重建那一步。一段 30s 1080p:软件 ~100s,换硬编也只到 ~80s——硬编只省下编码那部分。这反过来印证了:要真正实时,只能靠原生播放器在 GPU 上逐帧重建,转码方案本质是「转一次、缓存住」的权宜之计。 The IINA route first used software x265 for HDR10, making first-open slow. We added an Apple-Silicon hardware HEVC option (hevc_videotoolbox) to gvtools. But measurement showed: the transcode bottleneck is not the codec — it is the Python/numpy gain reconstruction. A 30 s 1080p clip: ~100 s software, ~80 s with hardware — the hardware only shaves the encode portion. Which confirms the point: true real-time has to be the native player reconstructing per-frame on the GPU; the transcode is a "do-it-once, cache it" stopgap.
