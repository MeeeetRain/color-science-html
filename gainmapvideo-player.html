视频版 gain map：一个向后兼容的
自适应 HDR 格式，和它的专利空间 A video gain map: a backward-compatible
adaptive-HDR format, and its patent space

gain map 让一张普通 SDR 画面额外带一层「增益」，由显示器按自身 HDR 余量自适应地提亮。这套在静态图上已经标准化（ISO 21496-1），但视频至今没有等价方案。GainmapVideo 把它带到视频：定义格式、做出两个播放器和一个格式转换工具，并在过程里梳理出可申报的专利方向。本文是第一人称的完整复盘。 A gain map adds an "amplification" layer to an ordinary SDR picture, brightened adaptively by the display to its own HDR headroom. This is standardized for still images (ISO 21496-1) but there is still no equivalent for video. GainmapVideo brings it to video: a format, two players, a format converter, and — along the way — a set of patentable directions. This is the full first-person retrospective.

00原理科普:一分钟看懂In plain terms: a one-minute primer

不需要任何技术背景,用一个比喻就能讲清楚。No technical background needed — one analogy does it.

🪟 比喻:一张照片 + 一张「亮度便签」🪟 Analogy: a photo + a "brightness sticky-note"

想象一张普通照片,旁边贴了一张便签。照片本身在任何屏幕上都正常显示(这就是 SDR,标准画面)。便签上写着:「窗外那片阳光,如果你的屏幕够亮,就调亮 4 倍。」老屏幕看不懂便签,照常显示;新的 HDR 屏幕读懂便签,把阳光真的点亮。gain map 就是这张便签——只不过它是逐像素的,精确记录画面里每个点该额外亮多少。 Picture an ordinary photo with a sticky-note beside it. The photo looks right on any screen (that's SDR — the standard picture). The note says: "that sunlight out the window — if your screen can go bright, make it 4× brighter." Old screens can't read the note and just show the photo; new HDR screens read it and actually light the sun up. A gain map is that note — except it's per-pixel, recording exactly how much extra brightness each spot may have.

① 底层:普通 SDR 视频① Base: an ordinary SDR video

谁都能播——手机、旧电视、浏览器,看到的就是一段正常视频。Anything plays it — phones, old TVs, browsers all just see a normal clip.

② 加层:逐帧「亮度便签」② Plus: a per-frame "brightness note"

一条额外的灰度视频,逐帧记录每个像素最多能提亮多少。老播放器自动忽略它。An extra grayscale track recording, frame by frame, how much each pixel may brighten. Old players just ignore it.

③ 播放:按屏幕余量点亮③ Playback: light up to the screen's budget

HDR 屏读「便签」,按自己当前能亮多少,把高光提到合适的亮度。An HDR screen reads the note and brightens highlights to whatever it currently can.

为什么叫「自适应」?Why "adaptive"?

关键点:屏幕能额外亮多少,不是固定的。有意思的是——你把屏幕亮度调得越高,留给 HDR 的「余量」反而越小(这正是我们排查了很久才明白的坑:不是软件坏,是屏幕在高亮度下没空间再亮了)。gain map 的妙处在于:它不写死「亮 4 倍」,而是写「最多亮 4 倍,屏幕有多少余量就用多少」。于是同一个文件,在手机、笔记本、HDR 电视上各自发挥到极限,你调亮度它也实时跟着变。 The key: how much extra brightness a screen has is not fixed. Counter-intuitively, the brighter you set the screen, the less headroom is left for HDR (exactly the trap that took us a long time to see — it wasn't a software bug, the panel simply has no room to go brighter at high brightness). The trick of a gain map: it doesn't hard-code "4× brighter," it says "up to 4×, use as much headroom as the screen has." So one file performs to the limit of a phone, a laptop, or an HDR TV — and tracks your brightness slider in real time.

那它跟视频有什么关系?And what's this got to do with video?

图片早就这么干了——iPhone 拍的 HDR 照片就是「SDR 照片 + gain 便签」。但视频一直没有公开的标准做法。GainmapVideo 把这套搬到视频:一条普通 SDR 视频(老播放器照常播)+ 一条逐帧 gain 视频 + 一小段说明,打包成一个文件。我们还为它做了播放器(把画面真正点亮)和转换工具(普通 HDR 与这个格式互转)。 Photos already do this — an iPhone HDR photo is just "SDR photo + gain note." But video had no open, standard way to do it. GainmapVideo brings it to video: a normal SDR video (legacy players play it as-is) + a per-frame gain video + a little metadata, packed into one file. We also built the players that actually light it up and a converter that moves ordinary HDR in and out of the format.

01为什么要做「视频版」gain mapWhy a video gain map

一个文件，SDR 设备照常播，HDR 设备按余量提亮。One file: SDR devices play it as-is, HDR devices brighten it to their headroom.

gain map 的核心：底层是一张标准 SDR 画面，旁边带一张「增益图」，告诉显示器在有 HDR 余量时每个像素该提亮多少。SDR 播放器无视增益图、照常显示；HDR 播放器按显示器当前能力把 SDR 重建成 HDR。和 Dolby Vision / HDR10+ 那种「参数化重映射元数据」不同，gain map 是逐像素的，空间信息直接编码在那层图里。 The idea: a standard SDR picture plus a "gain" image that says how much to brighten each pixel when HDR headroom exists. SDR players ignore the gain map; HDR players reconstruct SDR into HDR scaled to the display's current capability. Unlike the parametric remapping metadata of Dolby Vision / HDR10+, a gain map is per-pixel — the spatial information lives in that image layer.

向后兼容Backward compatible

底层就是标准 SDR 视频。QuickTime / VLC / 浏览器 <video> 当普通片子放，毫无感知。The base is a standard SDR video. QuickTime / VLC / browser <video> play it as an ordinary clip, none the wiser.

自适应显示Display-adaptive

同一个文件：屏幕能亮多少给多少，余量小少提、没余量退回 SDR。不像固定的 HDR10 主显示元数据烘死一档。One file: as much HDR as the screen allows — less boost on small headroom, pure SDR when there is none. Not baked to one level like fixed HDR10 mastering metadata.

逐像素，不是参数Per-pixel, not parametric

高光分布写在增益层里，比单条全局 tone curve 更贴合画面。Highlight distribution is in the gain layer — closer to the image than a single global tone curve.

02格式结构Format structure

两种封装：三件套（Profile A）和单文件（Profile B）。单文件才是有价值的形态。Two profiles: a sidecar triple (A) and a single file (B). The single file is the one that matters.

Profile A 是三件套：.sdr.mp4 + .gain.mp4 + .meta.json，便于调试。Profile B 是单个 .gv.mp4：一条标准 ISOBMFF 文件里，track 0 是 SDR base（默认轨），track 1 是 gain map（非默认，handler_name = GainmapVideo:gainmap），再加一个顶层 uuid box（UUID 47c8f1ff-…-b2c0）装 JSON 元数据。关键性质：不认识这个格式的 SDR 播放器只会看到并播放 track 0，一个文件就能分发。 Profile A is a sidecar triple (.sdr.mp4 + .gain.mp4 + .meta.json), handy for debugging. Profile B is a single .gv.mp4: one standard ISOBMFF file with track 0 = SDR base (default), track 1 = gain map (non-default, handler_name = GainmapVideo:gainmap), plus a top-level uuid box (UUID 47c8f1ff-…-b2c0) carrying JSON metadata. The key property: an SDR player that doesn't know the format sees and plays only track 0 — one file is enough to distribute.

元数据字段（ISO 21496-1 对齐）Metadata fields (ISO 21496-1 aligned)

GainMapMin / GainMapMax（对数增益的下/上限）、Gamma（码值非线性）、OffsetSDR / OffsetHDR（避免除零的小偏置）、HDRCapacityMin / HDRCapacityMax（内容假定的显示余量范围，HDRCapacityMax = log2(峰值/参考白)）、reference_white_nits（SDR 漫反射白对应的绝对亮度，把「SDR-in-HDR 该多亮」锚定下来）。 GainMapMin / GainMapMax (log-gain bounds), Gamma (code-value non-linearity), OffsetSDR / OffsetHDR (small offsets avoiding divide-by-zero), HDRCapacityMin / HDRCapacityMax (the headroom range the content assumes, HDRCapacityMax = log2(peak/refwhite)), and reference_white_nits (the absolute luminance of SDR diffuse white — anchors "how bright SDR-in-HDR should be").

03编码与重建数学Encoding & reconstruction math

编码（授权时）：对每个像素，由 HDR 与 SDR 的比值取对数得到增益，归一化到 [GainMapMin, GainMapMax]，再以 Gamma 非线性写成码值存进 gain 轨。重建（播放时）：反过来，并乘上一个随显示器余量变化的 weight。 Encoding (authoring): per pixel, take the log of HDR/SDR ratio to get gain, normalize into [GainMapMin, GainMapMax], then write a code value with the Gamma non-linearity into the gain track. Reconstruction (playback): the inverse, scaled by a weight that depends on the display's headroom.

# 重建 / reconstruction
g_log  = GainMapMin + pow(gCode, Gamma) · (GainMapMax − GainMapMin)
weight = clamp( (log2(displayHeadroom) − HDRCapacityMin) / (HDRCapacityMax − HDRCapacityMin), 0, 1 )
hdr    = (srgbEotf(sdr) + OffsetSDR) · 2(g_log · weight) − OffsetHDR

weight 是自适应的灵魂：它把「显示器现在有多少 HDR 余量」映射到 0~1。余量为 1×（log2=0）→ weight 趋 0 → 退回 SDR；余量足够大 → weight=1 → 满 HDR。原生播放器把 displayHeadroom 取成每一帧实时的系统 EDR 余量，所以调一下屏幕亮度，高光强度立刻跟着变。这套公式在我们的 WebGL 重建、Python CLI、Metal shader 三处逐字一致——单一数学来源，规避了实现间漂移。 The weight is the heart of the adaptation: it maps "how much HDR headroom the display has now" to 0..1. Headroom 1× (log2=0) → weight→0 → fall back to SDR; large enough headroom → weight=1 → full HDR. The native player reads displayHeadroom as the live, per-frame system EDR headroom, so nudging brightness changes highlight intensity instantly. This formula is identical, verbatim across our WebGL, Python CLI and Metal shader — one source of math, no drift.

04两个播放器Two players

浏览器路线一直被 EDR 输出折磨（Chrome 要实验开关、Safari 各版本不一、float16 backbuffer 不可靠）。于是换两条更干净的原生路：自研 Metal 播放器，和 IINA 插件。 The browser route kept fighting EDR output (Chrome needs an experimental flag, Safari varies by version, float16 backbuffers are unreliable). So we took two cleaner native roads: a Metal player and an IINA plugin.

为什么 IINA 走转码而不是实时？mpv 的自定义 shader 只能作用在单路视频上，没法把第二路实时解码的 gain 轨当成逐帧纹理喂进去；能塞两路的 --lavfi-complex 又做不了逐像素浮点合成。于是用「mpv 的强项（EDR 输出）绕开它的弱项（双路输入）」——代价是转码。原生播放器没有这个限制，直接双轨进 shader。 Why does IINA transcode? mpv's custom shaders operate on a single video; there is no clean way to feed a second live-decoded gain track as a per-frame texture, and the --lavfi-complex path that takes two inputs can't do per-pixel float compositing. So we lean on mpv's strength (EDR output) and route around its weakness (dual input) — at the cost of a transcode. The native player has no such limit and feeds both tracks straight into the shader.

EDR 显示链路The EDR display path

原生播放器的输出端是关键：一个 CAMetalLayer，开 wantsExtendedDynamicRangeContent，色彩空间 extendedLinearSRGB，像素格式 rgba16Float。在这个 layer 上 1.0 = SDR 白、>1.0 用显示器 EDR 余量。片源是 BT.709/sRGB，shader 直出线性 sRGB，与 layer 色域逐位对齐、零转换。 The output side is the crux: a CAMetalLayer with wantsExtendedDynamicRangeContent on, colorspace extendedLinearSRGB, format rgba16Float. On this layer 1.0 = SDR white and >1.0 uses EDR headroom. The source is BT.709/sRGB and the shader outputs linear sRGB — matching the layer's gamut exactly, no conversion.

07那个反直觉的教训The counter-intuitive lesson

⚠️ 让 HDR「不亮」的不是 bug，是屏幕亮度⚠️ What kept HDR dark wasn't a bug — it was screen brightness

我们排查了很久「为什么不进 HDR」：浏览器、IINA、原生播放器轮流试，改 probe、改 colorspace、改 shader……结果真正的根因是：macOS 在高亮度下根本不给 SDR 白以上的余量。系统报告的 maximumExtendedDynamicRangeColorComponentValue 在高亮度时坍缩到 1.0——任何 app 都没有空间把 HDR「亮出来」。渲染一直是对的，只是无处可亮。 We spent a long time on "why won't it enter HDR" — cycling through browser, IINA, native player, tweaking the probe, colorspace, shader… The actual root cause: at high brightness macOS reserves no headroom above SDR white. The reported maximumExtendedDynamicRangeColorComponentValue collapses to 1.0 — no app has room to show HDR. The rendering was correct all along; there was simply nowhere to be bright.

✅ 调低亮度，余量就回来了✅ Lower brightness, and the headroom returns

把屏幕亮度调低，current 余量立刻从 1.0× 往上爬（我们见过 6×，潜在 16×），weight 随之从 0 涨到 1，画面里的高光肉眼可见地亮过 SDR 白。排查 EDR 不亮，先调低亮度看余量，别急着怀疑代码。这也正是 gain map「自适应」的本意：余量是会变的量。 Lower the brightness and the current headroom climbs from 1.0× (we saw 6×, potential 16×); the weight rises 0 → 1 and highlights visibly exceed SDR white. When EDR won't light up, lower brightness and check headroom before suspecting the code. Which is exactly what gain-map "adaptation" is for: headroom is a variable.

硬件编码，以及一个意外发现Hardware encoding, and a surprise

IINA 路线最初用软件 x265 编 HDR10，首开慢。我们给 gvtools 加了 Apple Silicon 硬件 HEVC（hevc_videotoolbox）。但实测发现：转码慢的瓶颈不是编码器，而是 Python/numpy 做 gain 重建那一步。一段 30s 1080p：软件 ~100s，换硬编也只到 ~80s——硬编只省下编码那部分。这反过来印证：要真正实时，只能靠原生播放器在 GPU 上逐帧重建；转码本质是「转一次、缓存住」的权宜之计。 The IINA route first used software x265 for HDR10, making first-open slow. We added Apple-Silicon hardware HEVC (hevc_videotoolbox) to gvtools. But measurement showed: the bottleneck is not the codec — it is the Python/numpy gain reconstruction. A 30 s 1080p clip: ~100 s software, ~80 s hardware — the hardware only shaves the encode tail. Which confirms: true real-time has to be the native player reconstructing per-frame on the GPU; the transcode is a "do-it-once, cache it" stopgap.
